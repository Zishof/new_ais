# Phase 3 contract audit: Jenis Sekolah

## Decision

`sekolah.jenis_sekolah` is the selected first write aggregate for Phase 3. It is a bounded,
installation-global catalogue with six rows and one direct consumer relationship. It is suitable
for clone-only CRUD, but it is not approved for production writes. The source `ais` database stays
immutable and remains owned by the legacy application.

The machine-readable snapshot is
[`phase-3-jenis-sekolah-contract.json`](phase-3-jenis-sekolah-contract.json). The three authoritative
legacy files are fingerprinted there so drift can be detected before parity testing.

## Physical contract

The aggregate maps to `sekolah.jenis_sekolah`. Its identity is generated by
`sekolah.jenis_sekolah_id_seq`; `nama` is the only required business column. `jenjang` references
`public.jenjang(id)`. The physical audit-user column is lowercase `olehid`, even though the legacy
Java property is `olehId`.

`sekolah.sekolah.jenis_sekolah_id` is the only reverse foreign key and all 22 observed school rows
reference one of the six catalogue rows. Deletes must therefore surface a conflict instead of
cascading or hiding a constraint failure. No trigger or database uniqueness constraint protects
the table.

## Legacy behavior that must remain visible

- `nama` is required, searched with case-insensitive containment, and sorted ascending by default.
- The legacy form requires a `Jenjang`, although the database permits null.
- A null `aktif` value behaves as active. New legacy form records leave it null; the grid can later
  toggle it with UPDATE privilege.
- Name uniqueness is an exact, case-sensitive comparison after trimming the submitted value. It is
  enforced only in the legacy form, so imports can already create duplicates.
- The legacy active-only filter is defective and does not filter. AIS Next may expose a working
  active filter, but the unfiltered default must still make inactive records discoverable.
- The legacy Jenjang selector requires `jenjang.aktif = true`; the four currently referenced levels
  are inactive. AIS Next must use levels already referenced by current rows and must not silently
  reactivate the `jenjang` master.
- `JenisSekolah` is preloaded into the legacy in-memory cache. A database change is immediately
  query-visible but a running legacy JVM may require its documented cache refresh/restart before
  UI reverse-visibility can be claimed.

`nama` is consumed by official student/teacher reports and the public school landing profile.
Changing it is therefore externally visible even though the table contains no personal data.

## Authorization contract

Menu `881247`, label `Jenis Sekolah`, owns the legacy route
`/pages/master/sekolah/jenis_sekolah.zul`. Roles `am`, `amp`, and `kpsk` have all six legacy
privilege rows. However, effective authorization also requires `job_has_menu`: only `amp` and
`kpsk` have that menu assignment, and both roles are inactive. `am` is active and assigned to
active users but lacks the `job_has_menu` row, so it does not receive an effective authority.
Clone UAT therefore activates `amp` and assigns it to `admin.user_role2`; the source remains
unchanged.

AIS Next maps read/create/update/delete independently to `LEGACY_MENU_881247_<ACTION>`. Export
requires READ. Import is allowed only when CREATE, UPDATE, and DELETE are all present, matching the
legacy screen's stricter bulk-operation gate. Approve and reject are not meaningful CRUD actions
for this aggregate and must not be repurposed.

## Audit contract

Hibernate Envers writes a revision to `new_audit.revinfo` and a snapshot to
`new_audit.jenis_sekolah__audit`. Revision identifiers share `public.hibernate_sequence` with other
audited entities. The entity audit primary key is `(id, rev)`, with `revtype` values 0=create,
1=update, and 2=delete.

The inspected source contains no historical audit row for this entity. Parity must therefore be
proved on a clone. The business mutation, shared Envers revision, and entity audit snapshot must
commit or roll back together in the CORE database. Direct JDBC writes without those legacy audit
records are forbidden. An independent control-plane audit projection cannot be made atomic across
two PostgreSQL databases without XA; it remains a production gate until an outbox/reconciliation
design is approved and must never be described as part of the CORE atomic commit.

## Clone-only acceptance gates

Before changing ownership to `NEXT_WRITE` on the UAT clone, verify schema, row-count, relation, and
source fingerprints. Then prove:

1. List, filter, page, and sort parity, including null-active semantics.
2. Independent READ/CREATE/UPDATE/DELETE authorization and bulk-operation authorization.
3. Required-field, duplicate-name, missing-level, and foreign-key validation.
4. Create/update/active-toggle/delete Envers revisions and atomic rollback on audit failure.
5. Lost-update rejection through an explicit version token derived from the row snapshot.
6. Next-to-database visibility and database-to-Next visibility on the clone.
7. Referenced-row deletion returns conflict without changing business or audit data.
8. Route rollback survives an application restart without changing write ownership.
9. The source `ais` row counts and fingerprints remain unchanged.

Production promotion remains blocked until a business owner accepts the UAT behavior, the legacy
UI/cache reverse-visibility test has evidence, and the independent control-audit/outbox gap has an
approved design.
